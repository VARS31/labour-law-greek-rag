# Search report: database, embeddings and search (Phase 1B)

How the 5,740 labour-law chunks were stored in Postgres + pgvector, embedded with a local model and searched three ways. This file is generated by [`scripts/search_report.py`](../scripts/search_report.py) from measurements on this machine (Apple M5, Docker Desktop); the short comments under each question were written by hand after reading the results.

## At a glance

| | |
|---|---|
| Chunks in the database | 5,740 |
| Embedding model | `bge-m3` via Ollama, 1024 numbers per chunk |
| Embedding time | 5.2 minutes for 5,740 chunks (18.54 chunks per second, 1,947,458 tokens) |
| Database size | 111.9 MB in total, of which the chunks table 103.1 MB (Phase 0 estimated about 92 MB) |
| Semantic search, database part | 15.6 ms without an index, 1.7 ms with HNSW |
| Keyword search | 3.2 ms |
| Embedding the question | 21.5 ms (the slowest step) |
| Best method on the 8 questions | semantic on 5 questions, hybrid on 2, keyword (with hybrid) on 1; none found the construction-site act with the everyday word |

## How it is set up

- **Database:** Postgres 17 with pgvector 0.8.6 in Docker (`docker-compose.yml`), on port 5433 because Postgres.app already uses 5432. The data lives in a named Docker volume, so it survives restarts.
- **Schema:** `sql/001_extensions.sql` (pgvector, unaccent), `sql/002_text_search.sql` (the Greek full-text configuration), `sql/003_chunks.sql` (the table, every column commented), `sql/004_hnsw_index.sql` (the vector index, added after the first measurements).
- **Embeddings:** `embed_text` (the short source header plus the chunk text) is embedded with `bge-m3` through Ollama. All model calls go through `labour_rag/model_client.py`; the model name comes from `.env`.
- **Loading:** `python -m labour_rag.load` upserts every chunk by id and embeds only new or changed chunks (it stores a hash of `embed_text` and the model name), so running it again adds no duplicates and costs nothing.
- **Keyword search:** Postgres full-text search with the configuration `greek_labour`: accents removed (`unaccent`), Greek stemming, and a stopword list of 262 words (`sql/greek_labour.stop`). Postgres' own Greek configuration has no stopwords, so without the list words like "άρθρο" (in 68% of the chunks), "και" and "περί" would match almost everything. Any query word may match (OR); results are ranked by `ts_rank`, shortened for long chunks.
- **Semantic search:** cosine similarity between the question's embedding and each chunk's.
- **Hybrid search:** Reciprocal Rank Fusion. Each method gives its top 50; a chunk scores 1 / (60 + rank) in each list it appears in, and the scores are added.
- The question is cleaned with the same normalisation as the chunks before searching.

## Database size

Real sizes, measured with Postgres' own size functions, next to the Phase 0 estimate. Phase 0 assumed 5,301 chunks; there are 5,740.

| Part | Phase 0 estimate | Real |
|---|---:|---:|
| Chunk text (`text`) | 9.7 MB | 4.7 MB |
| Text to embed (`embed_text`, not in the estimate) | – | 5.2 MB |
| Vectors | 22.4 MB | 23.5 MB |
| Full-text column `fts` (not in the estimate) | – | 6.5 MB |
| Index `chunks_doc_idx` | – | 0.1 MB |
| Index `chunks_embedding_hnsw` | 43.4 MB | 47.0 MB |
| Index `chunks_fts_idx` | – | 3.4 MB |
| Index `chunks_pkey` | – | 0.2 MB |
| **Chunks table with all indexes** | **92.3 MB** (with 20% margin) | **103.1 MB** |
| Same, before the HNSW index | 40.2 MB | 56.1 MB |
| Whole database (including Postgres' own catalog) | – | 111.9 MB |

- **Text:** the two text columns hold 20.5 MB of UTF-8 text and take 9.9 MB on disk (Postgres compresses long values). The chunk text is stored twice (`text` and `embed_text`), which the Phase 0 estimate didn't count.
- **Vectors:** 4,100 bytes per chunk (4 bytes × 1024 numbers + 8 bytes header), stored uncompressed, as estimated.
- **HNSW index:** 8,193 bytes per chunk; Phase 0 assumed about 8,192 (one entry per 8 KB page). Real size 47.0 MB against an estimate of 43.4 MB for 5,301 chunks.
- Sizes are measured after `VACUUM FULL`, which rewrites the table without the dead row versions that updates leave behind. (Before that, a second load that rewrote every row had made the table about a third bigger.)
- **Total:** the chunks table with every index is 103.1 MB, above the Phase 0 estimate of 92.3 MB and 22% of the Supabase free plan's 500 MB (whole database).

## Search speed

Median of 7 runs per question, on the 8 questions below. *Database part* is the time Postgres takes once the question's embedding is ready; embedding the question with Ollama comes on top for semantic and hybrid search.

| | Without index | With HNSW |
|---|---:|---:|
| Embedding the question (Ollama) | 21.5 ms | same |
| Semantic, database part | 15.6 ms | 1.7 ms |
| Keyword (no embedding needed) | 3.2 ms | same (uses the full-text GIN index either way) |
| Hybrid, database part (two searches of 50 + fusion) | 19.9 ms | 6.4 ms |

- Query plan without the index: `Limit → Sort → Seq Scan` (every vector is compared, then sorted).
- Query plan with the index: `Limit → Index Scan using chunks_embedding_hnsw`.
- Building the HNSW index took 0.7 s and added 47.0 MB. Searches use `hnsw.ef_search = 100`, because an HNSW scan returns at most that many rows and hybrid search asks for 50.
- On the first try Postgres ignored the new index and kept scanning the whole table. The vectors are stored out of line (TOAST), and Postgres' planner doesn't count that cost, so the table looks cheap to scan; pgvector's README describes exactly this. Semantic search therefore switches sequential scans off for its one query (`SET enable_seqscan = off`, then `RESET`). Without an index Postgres still scans, because it has no other way.
- That switch had a side effect: it adds a huge artificial cost to the plan, which made Postgres compile the query to machine code (JIT) every time. JIT added about 27 ms to a scan of about 7 ms. JIT never pays off for queries this small, so the project's connections turn it off (`SET jit = off`).

**Did the index change the results?** HNSW is approximate. For semantic search the top 10 was identical (same chunks, same order) for 8 of the 8 questions, and on average 100% of the exact top 10 was found. For hybrid search the top 10 was identical for 7 of 8.

In plain words: the index makes the database part of semantic search 9× faster (15.6 ms → 1.7 ms), at the cost of 47.0 MB of disk space. Either way a whole search, including embedding the question (21.5 ms), takes well under a tenth of a second, so for 5,740 chunks the index is a nice-to-have. It matters more for the agent later, which runs several searches per question, and if more volumes are added.

### Overall

Semantic search is the strongest single method on these questions. It bridges everyday modern Greek and the katharevousa of the laws, and it isn't fooled by words with two meanings. Keyword search wins when the question repeats the words of a law's title, and fails on synonyms and ambiguous words. Hybrid with equal weights is the safest default for the Phase 1C baseline: it was never the worst of the three, and it had the main law at rank 1 in seven of the eight questions. But it also imports keyword noise, so a lower weight for the keyword list is worth testing on the Phase 2 evaluation set. No method fixes a vocabulary gap like "οικοδομές" versus "εργοτάξια"; that is a job for the Phase 3 rewriter. Near-identical chunks can fill the top 10 (see below), so the answer step will need to group repeats.
